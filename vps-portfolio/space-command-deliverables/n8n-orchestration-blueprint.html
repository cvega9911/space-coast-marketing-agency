Section 01

The Data Highway

Complete workflow pipeline from trigger to active outreach. Each node feeds the next in a strict sequential chain with branching logic at the quality-control gate. Arrows represent data flow direction.

🔗 Pipeline Architecture: Sequential with QC Branch

Nodes 1–5 run in strict sequence. Node 5 (Local LLM Engine) acts as the quality-control gate: approved prospects fork to Node 6A (HITL staging), while rejected/spam prospects route to Node 6B (skip logging). After human approval via Slack webhook, the flow continues to Instantly.ai for cold email delivery.

Section 02

Node-by-Node Technical Specifications

Detailed API contracts, headers, JSON bodies, and field mappings for every node in the pipeline. Use this as the authoritative reference for troubleshooting and extension.

🔔 Node 1: Trigger

Type: Schedule Trigger + Webhook

Cron: */15 * * * *

Webhook Path: /trigger/outreach-run

Purpose: Initiates each outreach cycle. The cron schedule ensures continuous operation; the webhook allows manual or event-driven triggering (e.g., after a new campaign is created).

📋 Node 2: Airtable CRM Reader

Method: GET

Endpoint: https://api.airtable.com/v0/{base_id}/Campaigns

Headers:

Authorization: Bearer {{AIRTABLE_API_KEY}}
Content-Type: application/json

Query Params: filterByFormula=AND({Status}="READY",{BatchProcessed}=0), maxRecords=10

Output Fields Needed:

  • client_id (Record ID)
  • client_url (Prospect website)
  • client_value_prop (Value proposition)
  • target_keyword (Search keyword)
  • client_name (Company name)
  • campaign_id (Campaign reference)

🔍 Node 3: Serper API

Method: POST

Endpoint: https://google.serper.dev/search

Headers:

X-API-KEY: {{SERPER_API_KEY}}
Content-Type: application/json

JSON Body:

{
"q": "{{target_keyword}}",
"num": 20,
"gl": "us",
"hl": "en"
}

Response Fields Used: organic[].link, organic[].title, organic[].snippet

🔀 Node 4: Split In Batches

Type: n8n native SplitInBatches node

Batch Size: 1

Options: Reset on each run = true

⚠️

Critical: Why Batch Size = 1

The Mac Mini M4 Pro has 64 GB unified memory shared between CPU and GPU. Each 30B-parameter model loaded into Ollama consumes ~18–20 GB. Processing multiple prospects concurrently would trigger memory pressure, causing the OS to swap and crater performance to unusable levels. Batch size 1 ensures the model loads, processes one prospect, and unloads before the next batch.

Security: HMAC Token

The approval webhook includes an HMAC-SHA256 token derived from the record ID + a shared secret. The webhook listener validates this before processing to prevent unauthorized approvals.

🪝 Node 8: Webhook Trigger

Type: Webhook (GET)

Path: /webhook/approve

Query Parameters:

On Approve: Updates Pitch status → "Approved," advances to Node 9.

On Reject: Updates Pitch status → "Rejected by Human," logs reason.

Section 03

Error Handling & Halting Logic

Production-grade resilience patterns that prevent cascading failures, resource exhaustion, and silent data loss. Every failure mode has a defined recovery path.

Context Timeout Guard

⏱️ 25-Second Timeout

The Execute Python Script node (Node 5) has a hard timeout of 25 seconds. If the LLM takes longer — due to a long webpage, model loading delays, or memory pressure — n8n terminates the execution and routes to the error handler.

🔄 Recovery Path

  • Route to: "Log Error" node → writes to Airtable Errors table
  • Error Log Fields: timestamp, node, error_message, prospect_url, batch_number
  • Then: Automatically advances to next batch
  • Retry: Flagged prospects retried on next cron cycle

Queue Concurrency Lock

🔒 Own Workflow Mode — No Parallel Execution

The workflow is configured with Own Workflow Mode, meaning only one instance can run at a time. If a cron trigger fires while the previous run is still processing, the new trigger is queued — not executed concurrently. This prevents:

  • Multiple LLM instances competing for VRAM simultaneously
  • Race conditions on Airtable reads/writes
  • Duplicate outreach to the same prospect
  • Instantly.ai rate-limit violations
ℹ️

Queue Behavior

Max queue depth: 1. If a trigger fires while a run is active AND the queue is full, the trigger is dropped with a log entry. This intentional design prevents backlog accumulation during LLM stalls.

VRAM OOM Protection

🧠 Memory Management Strategy

① Batch Size = 1

Every prospect processed individually. The LLM loads, processes one URL, produces one output, and releases memory before the next batch begins.

② Model Lifecycle Management

Python script calls ollama run qwen3:30b --keep-alive 0 to ensure the model is unloaded from VRAM immediately after inference completes. No lingering model in GPU memory.

③ Memory Watchdog

Before each batch, the script checks vm_stat for memory pressure. If available memory drops below 8 GB, the workflow pauses for 30 seconds to let the OS reclaim pages.

Section 04

Airtable Schema

Complete database design spanning four tables with relationships, field types, and usage context. Designed for n8n formula-style filtering and linked record traversal.

Table: Campaigns

Field Type Description
PK Record ID Auto-number Unique campaign identifier
Client Name Single line text Company or brand name
Client URL URL Client's website for context
Client Value Prop Long text The value proposition used for relevance matching
Target Keyword Single line text Google search keyword for prospect discovery
Status Single select READY, RUNNING, PAUSED, COMPLETED
Batch Processed Checkbox Toggle to mark campaign as fully processed
Instantly Campaign ID Single line text Linked Instantly.ai campaign for delivery
Prospects Link to Prospects Linked records in Prospects table
Created At Date/time Campaign creation timestamp

Table: Prospects

Field Type Description
PK Record ID Auto-number Unique prospect identifier
URL URL Prospect website URL
Domain Single line text Extracted domain for deduplication
Title (SERP) Single line text Google search result title
Status Single select New, Scraped, Reviewed: Approved, Skipped: Competitor, Skipped: Spam, Skipped: Irrelevant
Relevance Score Number (0–1) LLM-calculated relevance to client value prop
Scraped Insights Long text Key findings from webpage scrape
Campaign Link to Campaigns Parent campaign reference
Scanned At Date/time When this prospect was evaluated

Table: Pitches

Field Type Description
PK Record ID Auto-number Unique pitch identifier
Subject Single line text Drafted email subject line
Email Body Long text Full personalized email draft
Review Status Single select Pending Human Approval, Approved, Rejected by Human, Sent / Active Outreach, Bounced, Replied
Prospect Link to Prospects Linked prospect record
Campaign Link to Campaigns Parent campaign reference
Instantly Lead ID Single line text Instantly.ai lead identifier after sending
Sent At Date/time When email was delivered via Instantly
Opened At Date/time First open timestamp (from Instantly webhook)
Replied At Date/time Reply timestamp (from Instantly webhook)

Table: Approvals

Field Type Description
PK Record ID Auto-number Unique approval record
Pitch Link to Pitches Linked pitch being reviewed
Reviewer Single line text Slack username or identifier
Decision Single select Approved, Rejected, Needs Edit
Notes Long text Reviewer feedback or edit instructions
Decided At Date/time When the human made a decision

🔗 Relationship Summary

Campaigns 1→N Prospects (one campaign generates many prospects). Prospects 1→1 Pitches (each approved prospect gets one pitch). Pitches 1→1 Approvals (each pitch has one human approval record). The linked-record structure enables n8n to traverse relationships without additional API calls.

Section 05

Socratic Additions — Intelligent Enhancements

Socrates AI contributes four intelligent workflow extensions that transform the pipeline from a simple automaton into a self-monitoring, self-correcting outreach system.

📡 Deliverability Monitor

48-Hour Health Check

A separate n8n workflow runs every 6 hours, querying the Instantly.ai reporting API for all emails sent in the last 48 hours. It checks open rates per campaign and per sending domain.

🚨

Zero Opens = Spam Alert

If any campaign shows 0 opens after 48 hours with 20+ emails sent, the monitor immediately alerts Socrates via Slack with: the campaign name, sending domain, email volume, and a recommendation to pause and investigate (DNS/SPF/DKIM, domain reputation, copy audit).

Alert Template:

// Slack alert to #socrates-alerts when 0 opens detected 🚨 Deliverability Alert: {campaign_name} • Domain: {sending_domain} — 0 opens / {email_count} sent (48h) • Action: Campaign auto-paused. Check SPF/DKIM/DMARC, domain blacklists, and email copy for spam triggers. Manual review required before resuming.

📅 Follow-Up Scheduler

Automated Multi-Touch Sequence

When Node 10 confirms a Touch 1 email has been sent, the Follow-Up Scheduler automatically queues subsequent touches in Airtable with due dates. A separate cron workflow picks up due follow-ups and sends them via Instantly.

Touch Day Channel Template Strategy Condition
Touch 1 Day 0 Email (Instantly) Cold outreach — personalization hook Always sent
Touch 2 Day 3 Email (Instantly) Value-add follow-up — case study link No reply to Touch 1
Touch 3 Day 5 LinkedIn Connection request + note No reply to Touch 1 or 2
Touch 4 Day 7 Phone Call Task created for human CSM No reply, high-value prospect only
🛑

Auto-Stop on Reply

If Instantly detects a reply at any point, all subsequent scheduled touches for that prospect are automatically cancelled. The reply is routed to the human CSM via Slack with full context.

📊 Daily Summary Digest

End-of-Day Pipeline Report

Every day at 6:00 PM EST, a summary workflow queries all four Airtable tables and generates a Slack digest in the #daily-reports channel. The digest includes:

→ Sent
Emails delivered today
👁 Opened
Unique opens (all time)
↩ Replied
Replies received today
⏳ Pending
Awaiting human approval

🌡️ Instantly.ai Warm-Up Integration

New Domain Warm-Up Workflow

Before a new client's sending domain can be used for full-volume outreach, it must pass through Instantly's automated warm-up process. A separate n8n workflow manages this onboarding:

Step 1: Domain Registration

When a new Campaign is created with status "READY" and no existing Instantly Campaign ID, the warm-up workflow triggers. It registers the sending domain in Instantly via POST /api/v2/warmup/domains.

Step 2: DNS Verification

Checks SPF, DKIM, and DMARC records via DNS lookup. If records are missing, sends setup instructions to the client via Slack. Retries every 24 hours until verified.

Step 3: Warm-Up Progression

Monitors Instantly's warm-up dashboard via API. Progresses through: 5/day → 10/day → 20/day → 50/day → Full Volume. Each stage requires 3 days of healthy metrics (open rate > 20%, bounce rate < 5%).

Step 4: Green Light

When warm-up completes (typically 14–21 days), the workflow updates the Campaign with the Instantly Campaign ID and sets warmup_status = "COMPLETE". Socrates receives a Slack notification and the outreach pipeline can begin.

🧠 Socrates Oversight

Socrates monitors warm-up metrics daily. If a domain shows declining open rates during warm-up, Socrates pauses progression and alerts the team to investigate — preventing a damaged sender reputation before it impacts outreach volume.
