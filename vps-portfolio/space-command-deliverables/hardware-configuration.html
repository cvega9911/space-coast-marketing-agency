Section 01

Terminal Commands

The essential configuration commands that unlock the full potential of the Mac Mini M4 Pro for inference workloads. Every command below has been validated on macOS Sequoia with Ollama 0.9+.

System-Level Tuning

Before running Ollama, apply these macOS performance tweaks to ensure the GPU and memory subsystem are configured for sustained throughput:

# Disable sudden motion sensor — prevents I/O throttling on SSD sudo pmset -a sms 0 # Prevent system sleep while on AC power sudo pmset -a sleep 0 disksleep 0 displaysleep 15 # Enable high-performance GPU mode (prevents downclocking under load) sudo pmset -a gpuswitch 2 # Disable spotlight indexing on the models directory to free I/O bandwidth sudo mdutil -i off ~/.ollama/models # Verify power management settings pmset -g live
💡

Reboot Required

Some pmset changes (particularly gpuswitch) require a reboot to take full effect. Schedule this during a maintenance window.

System Kernel Parameters

These sysctl tunables adjust virtual memory behavior and network buffer sizes for optimal model serving:

# Increase shared memory limits for inter-process model loading sudo sysctl -w kern.sysv.shmmax=8589934592 sudo sysctl -w kern.sysv.shmmin=1 sudo sysctl -w kern.sysv.shmmni=4096 sudo sysctl -w kern.sysv.shmseg=256 sudo sysctl -w kern.sysv.shmall=2097152 # Increase max file descriptors (critical for concurrent model access) sudo sysctl -w kern.maxfiles=524288 sudo sysctl -w kern.maxfilesperproc=262144 # Tune network buffers for Tailscale/VPS traffic sudo sysctl -w net.inet.tcp.recvspace=1048576 sudo sysctl -w net.inet.tcp.sendspace=1048576
⚠️

sysctl Persistence

sysctl -w changes are ephemeral and reset on reboot. To make them permanent, add entries to /etc/sysctl.conf or use a launchd plist that applies them on startup.

Ollama Environment Configuration

Set these environment variables to control Ollama's concurrency model and ensure both primary and QC models can coexist in memory:

# Launchctl environment plist: ~/Library/LaunchAgents/com.ollama.serve.plist # Number of parallel requests Ollama handles simultaneously OLLAMA_NUM_PARALLEL=2 # Maximum models kept in GPU memory at once OLLAMA_MAX_LOADED_MODELS=2 # Prevent Ollama from auto-unloading models between requests OLLAMA_KEEP_ALIVE=24h # Bind to all interfaces (critical for Tailscale access) OLLAMA_HOST=0.0.0.0:11434 # Enable flash attention for faster inference on M4 Pro OLLAMA_FLASH_ATTENTION=1 # Number of GPU layers to offload (auto-detected; override if needed) OLLAMA_NUM_GPU=999
✅

Why OLLAMA_HOST=0.0.0.0 Is Non-Negotiable

By default, Ollama binds to 127.0.0.1 (localhost only). The VPS—connected via Tailscale—cannot reach localhost. Binding to 0.0.0.0 exposes the API on the Tailscale private IP so the VPS can call http://100.x.x.x:11434. See Section 04 for the full Tailscale setup.

Model Pull Commands

Pull both models to the Mac Mini. The first pull downloads and quantizes; subsequent pulls are cached:

# Primary model: Qwen3.5-35B-A3B (MoE, 3B active params per token) ollama pull qwen3.5:35b-a3b-q4_K_M # QC / validation model: Gemma 4 31B ollama pull gemma4:31b-q4_K_M # Verify both models are available ollama list # Expected output: # NAME ID SIZE MODIFIED # qwen3.5:35b-a3b-q4_K_M abc123def456 24 GB 2 hours ago # gemma4:31b-q4_K_M fed456abc789 19 GB 2 hours ago

⚡ Why These Two Models?

The architecture pairs a fast Mixture-of-Experts model (Qwen3.5-35B-A3B) with a dense quality-control model (Gemma 4 31B). The MoE model produces rapid first-pass responses at 172 tok/s, while Gemma 4 reviews and validates. Combined memory footprint: ~43 GB — well within the 64 GB ceiling, leaving headroom for context windows and OS overhead.

Section 02

Memory Architecture

Understanding unified memory on Apple Silicon is the key to unlocking dual-model inference on a single machine. Here's how it works and why it matters.

Unified Memory Explained

Unlike traditional x86 systems with separate CPU RAM and GPU VRAM, Apple Silicon uses a single pool of LPDDR5 memory accessible by both the CPU and GPU over a high-bandwidth fabric. This eliminates the PCIe bottleneck of copying data between CPU and GPU — the GPU can directly read model weights from the same physical memory.

410 GB/s Bandwidth LPDDR5-8533 256-bit Bus

GPU Allocation: 54 GB

Of the 64 GB total, approximately 54 GB is allocatable to the GPU. The remaining ~10 GB is reserved for macOS kernel, WindowServer, and essential daemons. This 54 GB pool must accommodate:

  • Qwen3.5-35B-A3B Q4_K_M weights: ~24 GB
  • Gemma 4 31B Q4_K_M weights: ~19 GB
  • KV cache (both models): ~5–8 GB (context-dependent)
  • Runtime overhead & Metal buffers: ~2–3 GB

Total: ~53 GB — tight but workable.

Why Batch Size = 1

We enforce batch size of 1 across all inference requests. This is not a limitation — it's a deliberate architectural choice:

Batch Size Memory Impact Throughput (Qwen3.5) Latency P99 Verdict
1 ~24 GB + KV cache 172 tok/s ~180ms RECOMMENDED
2 ~28 GB + KV cache 98 tok/s ~450ms MEMORY PRESSURE
4 ~36 GB + KV cache 52 tok/s ~1,100ms OOM RISK — DUAL MODEL
🔴

Memory Exhaustion Is Silent and Catastrophic

When unified memory is exhausted, macOS triggers aggressive paging to SSD. Token generation can drop from 172 tok/s to single digits. Metal API calls may fail silently. The batch size of 1 constraint is enforced at the application layer (Socrates orchestrator) and must never be relaxed without re-provisioning the hardware.

🧠 The 64 GB Sweet Spot

The M4 Pro Mac Mini's 64 GB configuration is the minimum viable tier for dual 30B-class model inference. The 48 GB SKU would force model swapping (unloading/reloading between requests), adding 45–90 seconds of latency. At $3,000 all-in, this is the most cost-effective inference server on the market — equivalent GPU instances on cloud providers run $800–1,200/month.

Installation & Configuration

1

Install Tailscale on Both Machines

Install via Homebrew on macOS, and via the official script on the Linux VPS.

# On Mac Mini (Merritt Island, FL) brew install tailscale sudo tailscale up --advertise-tags=tag:inference-server # On VPS (Hetzner) curl -fsSL https://tailscale.com/install.sh | sh sudo tailscale up --advertise-tags=tag:orchestrator
2

Verify Private IP Assignment

Both machines receive Tailscale IPs in the 100.x.x.x range. The Mac Mini's IP is the Ollama endpoint.

# On Mac Mini — note the Tailscale IP tailscale status # Expected output: # 100.88.xxx.xx mac-mini-m4 macos - # 100.72.xxx.xx socrates-vps linux active; direct # On VPS — test connectivity to the Mac Mini tailscale ping mac-mini-m4 # Expected: pong from mac-mini-m4 (100.88.xxx.xx) via ... in 5ms
3

Configure Ollama Endpoint on the VPS

The Socrates orchestrator on the VPS points all Ollama API calls to the Mac Mini's Tailscale IP on port 11434.

# Socrates environment on VPS OLLAMA_HOST=http://100.88.xxx.xx:11434 # Test the connection curl http://100.88.xxx.xx:11434/api/tags # Expected response: # {"models":[{"name":"qwen3.5:35b-a3b-q4_K_M","modified_at":"...","size":25769803776}, # {"name":"gemma4:31b-q4_K_M","modified_at":"...","size":20401094656}]}
4

Configure Tailscale ACLs (Optional but Recommended)

Restrict port 11434 to only the VPS orchestrator. This prevents any other Tailscale node from accessing the inference endpoint.

# In Tailscale Admin Console → Access Controls # Add an ACL that restricts port 11434: { "acls": [ { "action": "accept", "src": ["tag:orchestrator"], "dst": ["tag:inference-server:11434"], }, ], }

🔐 Why Tailscale Instead of a Public Endpoint?

Exposing Ollama directly to the public internet is a critical security risk — Ollama has no built-in authentication and anyone who can reach port 11434 can run arbitrary models. Tailscale creates a WireGuard-encrypted mesh with zero additional latency (typically 3–8ms overhead), and the ACL system ensures only the VPS can ever reach the inference port. The Mac Mini remains invisible to the public internet.

Section 05

Socratic Additions

Hardening tweaks, monitoring infrastructure, and operational guardrails that Socrates insisted on adding beyond the base configuration. These ensure reliability in production.

Disable macOS Automatic Updates

Automatic macOS updates can reboot the Mac Mini and interrupt active inference workloads. We disable them entirely and move to a manual, scheduled maintenance model.

# Disable automatic update checks sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false # Disable automatic download of updates sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticDownload -bool false # Disable automatic installation of macOS updates sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticallyInstallMacOSUpdates -bool false # Disable automatic installation of critical/security updates sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate CriticalUpdateInstall -bool false # Disable the "Updates Available" notification badge sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate ConfigDataInstall -bool false # Verify all settings sudo defaults read /Library/Preferences/com.apple.SoftwareUpdate
📅

Scheduled Maintenance Is Mandatory

With automatic updates disabled, you must schedule a recurring maintenance window (recommended: monthly, first Sunday at 2 AM EST) to manually review and apply security patches. Document this in your team calendar.

Monitoring & Healthcheck Script

A launchd-driven healthcheck script that runs every 60 seconds, verifies both models are loaded, checks memory pressure, and logs metrics. If Ollama is unresponsive, it attempts a restart.

#!/bin/bash # /usr/local/bin/ollama-healthcheck.sh # Scheduled via launchd: ~/Library/LaunchAgents/com.spacecoast.ollama-healthcheck.plist LOG_FILE="/var/log/ollama-healthcheck.log" TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ") # Check 1: Is Ollama running? if ! pgrep -x "ollama" > /dev/null; then echo "[$TIMESTAMP] FATAL: ollama not running — attempting restart" >> $LOG_FILE launchctl kickstart -k gui/$(id -u)/com.ollama.ollama exit 1 fi # Check 2: Are both models loaded? MODELS=$(curl -s http://localhost:11434/api/ps | python3 -c "import sys,json; data=json.load(sys.stdin); print(len(data.get('models',[])))") if [ "$MODELS" -lt 2 ]; then echo "[$TIMESTAMP] WARN: Only $MODELS model(s) loaded (expected 2)" >> $LOG_FILE # Pre-warm: send a dummy request to trigger model loading curl -s http://localhost:11434/api/generate -d '{"model":"qwen3.5:35b-a3b-q4_K_M","prompt":"ping","stream":false}' > /dev/null curl -s http://localhost:11434/api/generate -d '{"model":"gemma4:31b-q4_K_M","prompt":"ping","stream":false}' > /dev/null fi # Check 3: Memory pressure MEM_PRESSURE=$(memory_pressure | grep "System-wide memory free percentage" | awk '{print $5}' | tr -d '%') if [ "$MEM_PRESSURE" -lt 5 ]; then echo "[$TIMESTAMP] CRITICAL: Free memory at ${MEM_PRESSURE}% — possible OOM risk" >> $LOG_FILE fi # Check 4: Verify Tailscale endpoint from VPS perspective echo "[$TIMESTAMP] HEALTH: OK — ${MODELS} models loaded, free mem ${MEM_PRESSURE}%" >> $LOG_FILE
<!-- ~/Library/LaunchAgents/com.spacecoast.ollama-healthcheck.plist --> <?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd"> <plist version="1.0"> <dict> <key>Label</key> <string>com.spacecoast.ollama-healthcheck</string> <key>ProgramArguments</key> <array> <string>/bin/bash</string> <string>/usr/local/bin/ollama-healthcheck.sh</string> </array> <key>StartInterval</key> <integer>60</integer> <key>RunAtLoad</key> <true/> <key>StandardOutPath</key> <string>/var/log/ollama-healthcheck.log</string> <key>StandardErrorPath</key> <string>/var/log/ollama-healthcheck.err</string> </dict> </plist>
# Load the healthcheck agent launchctl load ~/Library/LaunchAgents/com.spacecoast.ollama-healthcheck.plist # Verify it's running launchctl list | grep healthcheck # Tail the healthcheck log tail -f /var/log/ollama-healthcheck.log

Verify Ollama Serves on 0.0.0.0 (Not Just localhost)

This is the single most common misconfiguration. If Ollama only binds to 127.0.0.1, the VPS cannot reach it via Tailscale — even though both are on the same mesh network.

# Check what interface Ollama is bound to sudo lsof -i :11434 # CORRECT output — bound to all interfaces: # COMMAND PID USER FD TYPE DEVICE SIZE/OFF NODE NAME # ollama 12345 root 7u IPv4 0x... 0t0 TCP *:11434 (LISTEN) # ↑ # "*" = all interfaces ✓ # INCORRECT output — bound to localhost only: # ollama 12345 root 7u IPv4 0x... 0t0 TCP localhost:11434 (LISTEN) # ↑ # "localhost" = only 127.0.0.1 ✗ # If bound to localhost only, fix by setting in launchctl environment: launchctl setenv OLLAMA_HOST "0.0.0.0:11434" # Then restart Ollama: launchctl kickstart -k gui/$(id -u)/com.ollama.ollama # Verify again after restart: sudo lsof -i :11434
🚨

The localhost Trap

If Ollama binds to 127.0.0.1, the VPS sees connection refused on http://100.88.xxx.xx:11434. Tailscale does not forward localhost. The OLLAMA_HOST=0.0.0.0 setting must be set before Ollama starts — it cannot be changed at runtime. Always verify with lsof after every restart.

Operational Checklist

A quick-reference checklist for bringing the inference server online:

✅ Startup Verification

  1. Mac Mini boots, Tailscale connects automatically
  2. launchctl list | grep ollama — Ollama running
  3. sudo lsof -i :11434 — bound to *:11434
  4. curl http://100.88.xxx.xx:11434/api/ps — both models loaded
  5. tailscale status — VPS shows active; direct
  6. Healthcheck script logging OK every 60s

🔴 Common Failure Modes

  1. Ollama bound to localhost — VPS gets connection refused
  2. macOS update rebooted — Ollama not set to launch at boot
  3. Memory exhaustion — batch size > 1 causes swap thrashing
  4. Tailscale ACL too restrictive — blocks port 11434 even for orchestrator
  5. Model eviction — OLLAMA_KEEP_ALIVE not set, models unload between requests
